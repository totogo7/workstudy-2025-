图书馆系统的测试可分为 4 层，每层目标和工具不同，对应你关心的核心场景：

| 测试类型     | 测试目标（核心场景）                               | 常用工具 / 框架                   | 关键特点（隔离性）             |
| ------------ | -------------------------------------------------- | --------------------------------- | ------------------------------ |
| 单元测试     | 测 Service 层核心逻辑（如借书时 “无副本返回失败”） | Mockito（Mock 依赖）+ JUnit 5     | 完全隔离外部依赖（不连 DB）    |
| 集成测试     | 测接口端到端逻辑（如 “调用借书接口→DB 状态正确”）  | SpringBootTest + MockMvc + H2     | 连轻量依赖（内存 DB/Redis）    |
| 并发测试     | 测并发安全（如 “同一副本不会被借两次”）            | JUnit 5 + 线程池 + CountDownLatch | 多线程模拟真实并发             |
| 缓存专项测试 | 测缓存逻辑（如 “缓存命中 / 失效、更新后缓存删除”） | SpringBootTest + RedisTemplate    | 连 Redis，验证缓存与 DB 一致性 |



### 1. 单元测试：隔离依赖，测 Service 层核心逻辑（借还逻辑）

#### （1）测试目标

验证 Service 层的 “纯业务逻辑” 是否正确，比如：

- 有可借副本时，借书成功（更新副本状态 + 插入借阅记录）；
- 无可用副本时，借书失败（返回 false，不插入记录）；
- 密码错误时，登录失败（返回 null）。

#### （2）核心思路：用 Mockito “Mock 外部依赖”

Service 层依赖 Mapper（如`BookCopyMapper`、`BorrowRecordMapper`），单元测试不连真实 DB，而是用**Mockito**模拟（Mock）这些 Mapper 的返回结果，只测 Service 层的逻辑判断。

#### （3）关键代码解析（对应你给的示例）

```4
// @SpringBootTest：启动Spring上下文，支持依赖注入
@SpringBootTest
public class BookServiceTest {

    // 1. @MockBean：用Mockito模拟BookCopyMapper（替代真实Mapper，不连DB）
    @MockBean
    private BookCopyMapper copyMapper;

    // 2. 同样Mock BorrowRecordMapper，隔离DB操作
    @MockBean
    private BorrowRecordMapper borrowMapper;

    // 3. 注入真实的BookService（要测的核心逻辑层）
    @Autowired
    private BookService bookService;

    // 测试场景1：有可借副本，借书成功
    @Test
    public void testBorrowSuccess() {
        // ① 模拟Mapper的返回结果：当查询bookId=1的可借副本时，返回copyId=100
        Mockito.when(copyMapper.findAvailableCopyForUpdate(1L)).thenReturn(100L);
        // ② 模拟Mapper的返回结果：当更新copyId=100的状态为2（已借）时，返回1（更新成功）
        Mockito.when(copyMapper.updateStatus(100L, 2)).thenReturn(1);

        // ③ 调用Service的借书方法（核心逻辑）
        boolean result = bookService.borrowBook(10L, 1L); // userId=10，bookId=1

        // ④ 断言结果：借书成功（result=true）
        Assertions.assertTrue(result);
        // ⑤ 验证Mapper方法被调用：BorrowRecordMapper的insert方法被调用1次（插入借阅记录）
        Mockito.verify(borrowMapper, Mockito.times(1)).insert(Mockito.any(BorrowRecord.class));
    }

    // 测试场景2：无可用副本，借书失败
    @Test
    public void testBorrowFail_NoAvailableCopy() {
        // ① 模拟Mapper返回：查询bookId=2的可借副本时，返回null（无副本）
        Mockito.when(copyMapper.findAvailableCopyForUpdate(2L)).thenReturn(null);

        // ② 调用Service方法
        boolean result = bookService.borrowBook(10L, 2L);

        // ③ 断言结果：借书失败（result=false）
        Assertions.assertFalse(result);
        // ④ 验证：BorrowRecordMapper的insert方法从未被调用（没插入记录）
        Mockito.verify(borrowMapper, Mockito.never()).insert(Mockito.any());
    }
}
```

- 快速定位问题：如果测试失败，能确定是 Service 层逻辑错（如判断条件写反），而非 Mapper 或 DB 问题；
- 效率高：不连 DB，测试用例执行快（毫秒级），适合频繁运行（如开发中实时验证）。



### 2. 集成测试：连依赖，测接口端到端逻辑（借还 + DB 状态）

#### （1）测试目标

验证 “接口→Service→Mapper→DB” 的端到端逻辑是否正确，比如：

- 调用`POST /books/borrow`接口后，DB 中副本状态变为 “已借”，借阅记录新增 1 条；
- 调用`GET /books`接口后，返回的可借数量与 DB 一致。

#### （2）核心思路：用 SpringBootTest + 内存 DB（H2）

- 不连真实 MySQL，而是用**H2 内存数据库**（启动快，测试后自动清空），避免污染真实数据；
- 用**MockMvc**模拟 HTTP 请求，调用 Controller 接口；
- 用**事务回滚**（`@Rollback`）保证测试用例之间的隔离（每个用例执行后，DB 回到初始状态）。

#### 3）关键代码示例（借还接口集成测试）

```java
// @SpringBootTest：启动Spring上下文
// @AutoConfigureMockMvc：自动配置MockMvc，用于模拟HTTP请求
@SpringBootTest
@AutoConfigureMockMvc
// @Rollback：测试结束后回滚事务，避免影响其他用例
@Rollback(true)
public class BookControllerIntegrationTest {

    // 注入MockMvc，模拟前端请求
    @Autowired
    private MockMvc mockMvc;

    // 注入JdbcTemplate，用于查询DB状态（验证结果）
    @Autowired
    private JdbcTemplate jdbcTemplate;

    // 测试场景：调用借书接口，验证DB状态正确
    @Test
    public void testBorrowInterface_EndToEnd() throws Exception {
        // ① 初始化测试数据：往book_copies表插入1个可借副本（copy_status=1）
        jdbcTemplate.update("INSERT INTO book_copies (id, book_id, copy_status) VALUES (100, 1, 1)");

        // ② 用MockMvc模拟前端POST请求：调用借书接口（userId=10，bookId=1）
        mockMvc.perform(post("/books/borrow") // 请求路径
                        .param("userId", "10") // 请求参数
                        .param("bookId", "1")
                        .contentType(MediaType.APPLICATION_FORM_URLENCODED)) // 请求类型
                // ③ 断言接口响应：状态码200，响应体包含“success”
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.code").value(1))
                .andExpect(jsonPath("$.msg").value("借书成功"));

        // ④ 验证DB状态：副本100的状态变为2（已借）
        Integer copyStatus = jdbcTemplate.queryForObject(
                "SELECT copy_status FROM book_copies WHERE id=100",
                Integer.class
        );
        Assertions.assertEquals(2, copyStatus);

        // ⑤ 验证DB状态：borrow_records表新增1条记录
        Long borrowCount = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM borrow_records WHERE user_id=10 AND book_id=1",
                Long.class
        );
        Assertions.assertEquals(1, borrowCount);
    }
}
```

#### （4）核心价值

- 验证端到端正确性：确保接口、Service、Mapper、DB 的交互无问题（比如 Mapper 的 SQL 是否写错、事务是否生效）；
- 接近真实场景：用 HTTP 请求模拟前端调用，用内存 DB 模拟真实存储，测试结果更可信。



### 3. 并发测试：模拟多线程，测并发安全（同一副本不被借两次）

#### （1）测试目标

验证 “并发借书” 场景下的数据一致性，核心是：**同一本可借副本，多个用户同时借，最终只有 1 人成功**（避免超借）。

#### （2）核心思路：多线程 + CountDownLatch+AtomicInteger

- 用`ExecutorService`创建线程池，模拟多个并发请求；
- 用`CountDownLatch`等待所有线程执行完毕（确保统计所有结果）；
- 用`AtomicInteger`统计成功次数（线程安全，避免计数错误）；
- 连真实 MySQL（或 Testcontainers 管理的 MySQL），因为 H2 内存 DB 的锁机制可能与真实 MySQL 不一致，测试结果更准确。

#### （3）关键代码解析（对应你给的示例）

```java
@SpringBootTest
// 禁用回滚，因为要观察多线程对DB的最终影响
@Rollback(false)
public class BookConcurrentTest {

    @Autowired
    private BookService bookService;

    @Autowired
    private JdbcTemplate jdbcTemplate;

    // 测试场景：2个用户同时借同一本书的最后1个副本
    @Test
    public void testConcurrentBorrow_NoOverBorrow() throws InterruptedException {
        // ① 初始化测试数据：插入1个可借副本（bookId=1，copyId=200，status=1）
        jdbcTemplate.update("INSERT INTO book_copies (id, book_id, copy_status) VALUES (200, 1, 1)");

        // ② 线程池：创建2个线程（模拟2个并发用户）
        ExecutorService executor = Executors.newFixedThreadPool(2);
        // CountDownLatch：等待2个线程都执行完再统计结果
        CountDownLatch latch = new CountDownLatch(2);
        // AtomicInteger：统计借书成功的次数（线程安全）
        AtomicInteger successCount = new AtomicInteger(0);

        // ③ 定义并发任务（每个任务模拟1个用户借书）
        Runnable borrowTask = () -> {
            try {
                // 生成不同的userId（避免用户重复）
                Long userId = 100L + ThreadLocalRandom.current().nextInt(100);
                // 调用借书方法，成功则计数+1
                if (bookService.borrowBook(userId, 1L)) {
                    successCount.incrementAndGet();
                }
            } finally {
                // 线程执行完，计数器减1
                latch.countDown();
            }
        };

        // ④ 提交2个并发任务
        executor.submit(borrowTask);
        executor.submit(borrowTask);

        // ⑤ 等待所有线程执行完毕（最多等5秒，避免死等）
        latch.await(5, TimeUnit.SECONDS);
        // 关闭线程池
        executor.shutdown();

        // ⑥ 断言结果：成功次数只能是1（同一副本只能被借1次）
        Assertions.assertEquals(1, successCount.get());

        // ⑦ 验证DB状态：副本200的状态是2（已借），且borrow_records只有1条记录
        Integer copyStatus = jdbcTemplate.queryForObject(
                "SELECT copy_status FROM book_copies WHERE id=200",
                Integer.class
        );
        Assertions.assertEquals(2, copyStatus);

        Long borrowCount = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM borrow_records WHERE book_id=1",
                Long.class
        );
        Assertions.assertEquals(1, borrowCount);

        // ⑧ 清理测试数据（避免影响其他用例）
        jdbcTemplate.update("DELETE FROM borrow_records WHERE book_id=1");
        jdbcTemplate.update("DELETE FROM book_copies WHERE id=200");
    }
}
```

#### （4）核心价值

- 暴露并发问题：如果没加锁（如`SELECT ... FOR UPDATE`），测试会出现`successCount=2`，证明存在超借风险；
- 验证锁机制有效性：加锁后`successCount=1`，证明悲观锁 / 乐观锁能保证并发安全。



### 4. 缓存专项测试：测缓存逻辑（命中、失效、一致性）

#### （1）测试目标

验证缓存策略是否正确，核心场景：

- 缓存命中：第一次查 DB，第二次查缓存；
- 缓存失效：TTL 到期后，重新查 DB 并回写缓存；
- 缓存一致性：更新图书后，缓存被删除（下次查 DB 获取最新数据）。

#### （2）核心思路：用 RedisTemplate 操作缓存，验证缓存状态

```java
@SpringBootTest
public class BookCacheTest {

    @Autowired
    private BookCacheService bookCacheService;

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    @Autowired
    private BookMapper bookMapper;

    private static final String BOOK_CACHE_KEY = "book:summary:1";

    // 测试场景1：缓存未命中→查DB→回写缓存
    @Test
    public void testCacheMiss_WriteBack() {
        // ① 先删除缓存（确保初始状态无缓存）
        redisTemplate.delete(BOOK_CACHE_KEY);

        // ② 第一次查询：缓存未命中，查DB
        Book book = bookCacheService.getBook(1L);
        Assertions.assertNotNull(book);

        // ③ 验证缓存已回写：Redis中存在该缓存
        Boolean hasCache = redisTemplate.hasKey(BOOK_CACHE_KEY);
        Assertions.assertTrue(hasCache);

        // ④ 验证缓存内容正确：缓存中的bookId=1
        Book cachedBook = (Book) redisTemplate.opsForValue().get(BOOK_CACHE_KEY);
        Assertions.assertEquals(1L, cachedBook.getId());
    }

    // 测试场景2：缓存命中→直接返回缓存（不查DB）
    @Test
    public void testCacheHit_ReturnDirectly() {
        // ① 手动往Redis写入缓存
        Book mockBook = new Book();
        mockBook.setId(1L);
        mockBook.setTitle("缓存测试书");
        redisTemplate.opsForValue().set(BOOK_CACHE_KEY, mockBook, 10, TimeUnit.MINUTES);

        // ② 调用查询方法
        Book book = bookCacheService.getBook(1L);

        // ③ 断言：返回的是缓存中的数据（标题是“缓存测试书”，而非DB中的真实标题）
        Assertions.assertEquals("缓存测试书", book.getTitle());

        // ④ 验证：DB未被调用（用Mockito模拟Mapper，验证查询方法未执行）
        // （实际项目中可Mock BookMapper，此处简化）
    }

    // 测试场景3：更新图书→删除缓存（保证一致性）
    @Test
    public void testUpdateBook_DeleteCache() {
        // ① 初始化缓存和DB数据
        Book dbBook = bookMapper.findById(1L);
        redisTemplate.opsForValue().set(BOOK_CACHE_KEY, dbBook, 10, TimeUnit.MINUTES);

        // ② 更新图书信息（模拟编辑书名）
        dbBook.setTitle("更新后的书名");
        bookMapper.update(dbBook);
        // 调用更新后的缓存清理方法（实际项目中在updateBook服务中自动调用）
        bookCacheService.invalidateBook(1L);

        // ③ 验证缓存已删除：Redis中无该缓存
        Boolean hasCache = redisTemplate.hasKey(BOOK_CACHE_KEY);
        Assertions.assertFalse(hasCache);

        // ④ 验证下次查询获取最新数据：查DB，返回更新后的书名
        Book newBook = bookCacheService.getBook(1L);
        Assertions.assertEquals("更新后的书名", newBook.getTitle());
    }
}
```

## 四、应对追问：提前准备高频问题

### 追问 1：并发测试用 H2 不准确怎么办？

H2 是 “内存数据库”，虽然轻量快，但它的**锁机制、事务隔离级别**和真实的 MySQL 有差异 —— 比如 H2 对`SELECT ... FOR UPDATE`（行锁）的实现比较简单，可能在并发测试中 “没锁住”，导致测试结果看起来 “并发安全”，但实际部署到 MySQL 后却出现超借问题（相当于 “模拟考和真实考的规则不一样”）。

核心需求：**让测试环境的数据库和生产环境一致（都用 MySQL），但又不能污染本地 MySQL 数据**。

解决方案：Testcontainers（“临时 MySQL 容器”）

Testcontainers 是一个工具，能在测试时**自动启动一个真实的 MySQL 容器（Docker 容器）**，测试结束后自动销毁容器 —— 相当于 “每次测试都搭一个临时的、干净的 MySQL 环境”，既保证和生产环境一致，又不影响本地数据。

“H2 内存数据库的行级锁机制（如 FOR UPDATE）可能与真实 MySQL 不一致，导致测试结果失真。实际项目中会用**Testcontainers**（Docker 管理的真实 MySQL 容器），测试时自动启动 MySQL 容器，测试后销毁，既保证结果准确，又不污染本地环境。”

### 追问 2：怎么把测试集成到 CI/CD（自动化）？

- **CI（持续集成）**：开发人员每次提交代码（比如推到 GitHub），系统自动跑 “编译→测试→检查代码规范”，如果测试失败，立刻通知开发（避免有 bug 的代码累积）；
- **CD（持续部署）**：测试通过后，系统自动把代码部署到测试 / 生产环境（可选，图书馆项目一般先部署到测试环境）。

核心需求：**让测试 “自动化”，不用手动跑 —— 代码提交后，系统自己验证，过了才能合并 / 部署**。

解决方案：GitHub Actions（或 GitLab CI）:以最常用的 GitHub Actions 为例，它是 GitHub 自带的 CI/CD 工具，能通过一个配置文件（`.github/workflows/test.yml`）定义 “代码提交后要做什么”—— 比如启动 MySQL/Redis，执行所有测试用例，判断是否通过。

#### 步骤 1：在项目根目录创建配置文件

在后端项目的`.github/workflows/`文件夹下新建`test.yml`（名字随便，后缀是.yml），内容如下：

```yaml
# 工作流名称：图书馆项目自动化测试
name: Library Test CI

# 触发条件：当代码推到main分支，或有人提PR到main分支时，自动执行
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

# 工作流的“任务”（在Ubuntu系统上执行）
jobs:
  test:
    runs-on: ubuntu-latest # 用Ubuntu系统（免费，速度快）

    # 服务依赖：启动MySQL和Redis容器（和Testcontainers类似，用Docker）
    services:
      # 启动MySQL 8.0容器
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: test_library
        ports:
          - 3306:3306 # 端口映射：容器3306→系统3306
        options: >-
          --health-cmd "mysqladmin ping"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

      # 启动Redis容器（用于缓存测试）
      redis:
        image: redis:6.2
        ports:
          - 6379:6379
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    # 具体执行步骤
    steps:
      # 步骤1：拉取代码到Ubuntu系统
      - uses: actions/checkout@v4

      # 步骤2：安装JDK 17（图书馆项目用的Java版本）
      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      # 步骤3：执行测试用例（用Maven跑所有测试，包括单元+集成+并发）
      - name: Run Tests
        run: ./mvnw test # Maven命令：执行src/test下的所有测试
        # 给测试传递MySQL/Redis的连接信息（告诉项目连服务里的MySQL/Redis）
        env:
          SPRING_DATASOURCE_URL: jdbc:mysql://localhost:3306/test_library?useSSL=false
          SPRING_DATASOURCE_USERNAME: root
          SPRING_DATASOURCE_PASSWORD: root
          SPRING_REDIS_HOST: localhost
          SPRING_REDIS_PORT: 6379
```

#### 提交代码触发 CI

### 追问 3：怎么测缓存雪崩 / 穿透？

缓存穿透是 “用户频繁查不存在的 bookId（比如`-1`、`999999`），缓存没命中，每次都查 DB”—— 测试要验证 “这种请求不会频繁打到 DB”。

**构造不存在的 ID→查缓存→查 DB→验证 “第一次查 DB，之后查缓存空对象，DB 只查 1 次”**。



缓存雪崩是 “大量图书缓存的 TTL 相同（比如都设 10 分钟），同一时间全部过期，所有查询瞬间落到 DB”—— 测试要验证 “加了随机 TTL 后，缓存不会同时过期，DB 压力平稳”。

**批量插入缓存（设置相同 TTL vs 随机 TTL）→监控 TTL 到期时的 DB 查询次数→验证 “随机 TTL 下 DB 查询次数无骤增”**。

“测缓存穿透：构造不存在的 bookId，断言 Redis 会缓存空对象，且 DB 查询次数 = 1；测缓存雪崩：批量插入 100 个图书缓存，设置相同 TTL，用定时任务监控 TTL 到期时 DB 的 QPS，断言 QPS 无骤增（因为我们加了随机 TTL）。”

通过这种结构化回答，既能展示你对测试分层的理解，又能结合业务场景说明落地方法，还能应对追问，让面试官觉得你 “不仅会写代码，还懂如何保证代码正确”。
