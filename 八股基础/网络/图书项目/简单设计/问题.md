# 1) 并发借书（如何保证同一本副本不会被并发借出两次？）

**考点**：数据库并发、事务、悲观/乐观锁、事务隔离、数据一致性。面试官常看你是否理解并发场景并能给出可落地方案。

### 面试答法（背版）

> 在借书场景，我们用事务保证并发安全。实现上我用 `SELECT ... FOR UPDATE`（悲观锁）在事务内锁定一个“可借副本（book_copies）”，然后更新副本状态并插入借阅记录，最后提交。这样两个并发请求无法同时拿到同一行。若系统需要更高吞吐，我也实现过基于 `available_copies` 的乐观锁（version 或 where available_copies>0 的 CAS 更新）并结合 Redis 预减库存做短期优化。

悲观锁的核心思想：**“先锁住资源，再操作”** —— 只要一个用户开始处理某个副本，就把这个副本 “锁起来”，其他用户必须等锁释放后才能操作。结合事务，确保整个借书流程的原子性。

逻辑简单，安全性高，能 100% 保证数据一致性，适合 “并发不极高” 的场景（比如校园图书馆，同时借书的用户不会太多）。

缺点：会产生锁等待（比如多个用户抢同一本书的最后一个副本，后面的用户要等前面的完成），并发量极高时（比如秒杀场景）会导致响应变慢，甚至出现死锁（需合理设计索引避免）。

### 关键代码（Service 层伪实操）

```java
// BookService.java
public interface BookService {
    boolean borrowBook(Long userId, Long bookId);
}

// BookServiceImpl.java
@Service
public class BookServiceImpl implements BookService {

    @Resource
    private BookMapper bookMapper;
    @Resource
    private BookCopyMapper copyMapper;
    @Resource
    private BorrowRecordMapper borrowMapper;

    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean borrowBook(Long userId, Long bookId) {
        // 1. 查找一个可借的副本并锁行（FOR UPDATE）
        Long copyId = copyMapper.findAvailableCopyForUpdate(bookId);
        if (copyId == null) {
            return false; // 没有可借副本，可以返回提示或加入预约队列
        }
        // 2. 标记副本为已借（状态更新）
        int updated = copyMapper.updateStatus(copyId, BookCopyStatus.BORROWED);
        if (updated != 1) {
            throw new IllegalStateException("并发冲突，借书失败");
        }
        // 3. 插入借阅记录
        BorrowRecord r = new BorrowRecord();
        r.setUserId(userId);
        r.setCopyId(copyId);
        r.setBookId(bookId);
        r.setBorrowTime(LocalDateTime.now());
        r.setDueTime(LocalDateTime.now().plusDays(30));
        borrowMapper.insert(r);

        // 4. 同步 books.available_copies -1（可放在触发器或应用中）
        bookMapper.decreaseAvailableCopies(bookId);

        return true;
    }
}
```

对应 Mapper（MyBatis 注解/SQL）示例：

```java
// BookCopyMapper.java
@Mapper
public interface BookCopyMapper {
     /**
     * 查找某本书的1个可借副本，并对该行加“行锁”
     * @param bookId 图书ID
     * @return 可借副本的ID（若没有则返回null）
     */
    @Select("SELECT id FROM book_copies " +
            "WHERE book_id = #{bookId} AND copy_status = 1 " + // copy_status=1：可借
            "LIMIT 1 " + // 只取1个副本（避免锁多行）
            "FOR UPDATE") // 关键：对查询到的行加“排他锁”，其他事务无法修改或加锁
    
    Long findAvailableCopyForUpdate(@Param("bookId") Long bookId);

     /**
     * 更新副本状态
     * @param copyId 副本ID
     * @param status 目标状态（2=已借）
     * @return 影响行数（1=成功，0=失败）
     */
    @Update("UPDATE book_copies SET copy_status = #{status} WHERE id = #{copyId} AND copy_status = 1") // 二次校验：确保副本还是可借状态
    int updateStatus(@Param("copyId") Long copyId, @Param("status") int status);
}
```

- `FOR UPDATE`的作用：

  当事务 A 执行这个 SQL 查到副本 101 后，会对book_copies.id=101 这一行加 “排他锁”。此时事务 B 再执行同样的 SQL，会被阻塞（等待事务 A 释放锁），直到 A 提交或回滚。这样就避免了 A 和 B 同时查到副本 101 的情况。

### 可能追问 & 回答要点

- **追问1**：`FOR UPDATE` 会锁住多少行？会造成性能问题么？
   → 回答：只锁定选中的行（或锁住扫描到的行，根据索引情况），在并发不非常高的校园应用可接受。高并发下可考虑乐观锁+Redis预减库存或用消息队列串行化分配副本。
- **追问2**：为什么还要维护 books.available_copies？一致性如何保证？
   → 回答：`available_copies` 是冗余字段用于快速查询，必须在同一事务内更新（或用触发器）；否则会出现短暂不一致。我们在借还事务中同时更新它，或在归还/借出操作后同步缓存。



## 方案 2：乐观锁 —— 高并发场景的优化（适合并发极高场景）

如果图书馆用户量极大（比如百万级用户同时借书），悲观锁的锁等待会成为性能瓶颈，此时适合用**乐观锁**。

乐观锁的核心思想：**“先操作，再校验”** —— 不主动加锁，而是通过 “版本号” 或 “状态字段” 判断操作期间是否有其他事务修改了数据，若有则重试。



### 1. 实现方式：基于 “版本号” 或 “可用数量 CAS”

这里以 “副本表加版本号” 为例，步骤如下：

#### （1）修改副本表结构（加 version 字段）

```sql
ALTER TABLE book_copies ADD COLUMN version INT NOT NULL DEFAULT 0 COMMENT '版本号，用于乐观锁';
```

- 每次更新副本时，`version`字段加 1；
- 更新时必须校验`version`是否和查询时一致（若一致，说明没被修改；若不一致，说明被其他事务修改，需重试）。

#### （2）Mapper 层：乐观锁查询与更新

```java
@Mapper
public interface BookCopyMapper {
    /**
     * 乐观锁：查询可借副本（获取当前version）
     */
    @Select("SELECT id, version FROM book_copies " +
            "WHERE book_id = #{bookId} AND copy_status = 1 " +
            "LIMIT 1")
    BookCopyVO findAvailableCopyWithVersion(@Param("bookId") Long bookId); // BookCopyVO：包含id和version

    /**
     * 乐观锁：更新副本状态（校验version）
     */
    @Update("UPDATE book_copies " +
            "SET copy_status = #{status}, version = version + 1 " + // 版本号+1
            "WHERE id = #{copyId} AND copy_status = 1 AND version = #{version}") // 校验version
    int updateStatusWithOptimisticLock(
            @Param("copyId") Long copyId,
            @Param("status") int status,
            @Param("version") int version
    );
}
```

#### （3）Service 层：重试机制

```java
@Service
public class BookServiceImpl implements BookService {

    // 重试次数（避免无限重试）
    private static final int MAX_RETRY = 3;

    @Override
    @Transactional(rollbackFor = Exception.class)
    public boolean borrowBook(Long userId, Long bookId) {
        // 重试机制：最多重试3次，失败则返回
        for (int i = 0; i < MAX_RETRY; i++) {
            // 步骤1：查询可借副本（带version）
            BookCopyVO copyVO = copyMapper.findAvailableCopyWithVersion(bookId);
            if (copyVO == null) {
                return false; // 无可用副本
            }

            // 步骤2：更新副本状态（校验version）
            int updateCount = copyMapper.updateStatusWithOptimisticLock(
                    copyVO.getId(), 2, copyVO.getVersion()
            );

            if (updateCount == 1) {
                // 步骤3：更新成功，插入借阅记录和可用数量（后续步骤同悲观锁）
                BorrowRecord record = new BorrowRecord();
                // ... 赋值省略
                borrowMapper.insert(record);
                bookMapper.decreaseAvailableCopies(bookId);
                return true;
            }

            // 更新失败（version不一致），重试（短暂休眠避免频繁重试）
            try {
                Thread.sleep(10); // 休眠10ms，减少CPU占用
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }

        // 重试3次仍失败，返回并发冲突
        throw new IllegalStateException("当前借书人数过多，请稍后重试");
    }
}
```

- 核心逻辑：每次查询副本时，获取当前的version；更新时，只有version和查询时一致的记录才会被更新（where version = #{version}）。如果有其他事务修改了副本（version已加 1），当前更新会失败（影响行数 0），触发重试，直到成功或达到最大重试次数。
- 优点：无锁等待，并发性能高，适合高并发场景；
- 缺点：有 “重试成本”（失败后需重试），逻辑比悲观锁复杂，适合 “冲突概率低” 的场景（比如某本书有很多可借副本，冲突少）。

# 2) Redis 缓存策略（书目缓存 & 热门榜单如何设计与失效策略）

**考点**：缓存模式（Cache-Aside、Write-Through、Write-Behind）、缓存一致性、热点/雪崩/穿透、Redis 数据结构应用。

要设计合理的 Redis 缓存策略，核心是解决 **“数据读取性能” 与 “缓存一致性”**的平衡问题，同时针对 “热门数据” 做专项优化。结合 “书目缓存” 和 “热门榜单” 场景，下面从**缓存模式选择→核心设计细节→失效策略→问题解决方案 ** 四个维度展开，确保每个环节都能落地且可解释。

### 面试答法（背版）

> 我采用 Cache-Aside（客户端主动缓存）策略：读取先查 Redis（key: `book:summary:{id}`），命中直接返回；未命中则从 DB 查并回写 Redis（设置合理 TTL）。更新书目时（新增/编辑/删除/借出/归还）会同步删除或更新缓存，确保一致性。热门榜单用 Redis ZSET（`book:popular`），在用户借阅或查看时 `ZINCRBY` 更新分数，定时把 TopN 写回 `book:summary` 供前端快速展示。

## 一、书目缓存设计：Cache-Aside 模式（最实用的缓存策略）

书目信息（如图书详情、可借数量）是高频读取数据（用户浏览、查询时频繁访问），但更新频率较低（新增 / 编辑图书时才变更），适合用**Cache-Aside 模式（旁路缓存）**—— 

由应用程序主动管理缓存，读取时 “查缓存→无则查 DB→回写缓存”，更新时 “更 DB→删缓存”。

### 1. 核心设计：数据结构与缓存 Key

#### （1）数据结构选择

- 书目信息是结构化数据（id、title、author、availableCopies 等），用**Redis String 类型**存储（序列化方式选 JSON，便于前端直接解析）。
- 示例：`book:summary:1001 → {"id":1001,"title":"活着","author":"余华","availableCopies":5,...}`

#### （2）缓存 Key 命名规范

采用`业务:数据类型:唯一标识`格式，清晰且便于管理：

- 单本书目缓存：`book:summary:{bookId}`（如`book:summary:1001`）
- 批量书目缓存（可选）：`book:batch:{ids}`（如`book:batch:1001,1002`，缓存多个图书信息，减少多次查询）

### 2. 读写流程（附代码解析）

#### （1）读取流程：“缓存优先，DB 兜底”

```java
@Service
public class BookCacheService {
    @Resource
    private RedisTemplate<String, Object> redisTemplate;
    @Resource
    private BookMapper bookMapper;

    // 缓存Key前缀
    private static final String BOOK_KEY_PREFIX = "book:summary:";
    // 缓存默认过期时间：10分钟（可根据更新频率调整）
    private static final long BOOK_TTL = 10;

    /**
     * 读取图书信息（缓存优先）
     */
    public Book getBook(Long bookId) {
        if (bookId == null) return null;
        
        String key = BOOK_KEY_PREFIX + bookId;
        // 步骤1：先查Redis缓存
        Book book = (Book) redisTemplate.opsForValue().get(key);
        if (book != null) {
            return book; // 缓存命中，直接返回
        }
        
        // 步骤2：缓存未命中，查数据库
        book = bookMapper.findById(bookId); // 假设Mapper有此方法
        if (book != null) {
            // 步骤3：回写Redis（设置TTL，避免缓存永久有效）
            redisTemplate.opsForValue().set(key, book, BOOK_TTL, TimeUnit.MINUTES);
        } else {
            // 处理缓存穿透：缓存空对象（短TTL，如1分钟）
            redisTemplate.opsForValue().set(key, new Book(), 1, TimeUnit.MINUTES);
        }
        return book;
    }
}
```

#### （2）更新流程：“先更 DB，再删缓存”

当图书信息变更（如编辑书名、归还后更新可借数量）时，必须保证缓存与 DB 一致，流程如下：

```java
/**
 * 更新图书信息（保证缓存一致性）
 */
@Transactional(rollbackFor = Exception.class)
public void updateBook(Book book) {
    // 步骤1：先更新数据库（确保数据持久化）
    bookMapper.update(book); // 更新DB中的图书信息
    
    // 步骤2：删除对应缓存（而非直接更新缓存）
    String key = BOOK_KEY_PREFIX + book.getId();
    redisTemplate.delete(key);
}
```

**为什么 “删缓存” 而不是 “更新缓存”？**

- 避免并发更新问题：假设线程 A 更新 DB 后准备更新缓存，线程 B 此时也更新 DB 并先更新了缓存，线程 A 的更新会覆盖线程 B 的结果，导致不一致；
- 删缓存更简单：删除后，下一次查询会自动从 DB 加载最新数据并回写缓存，天然保证一致性。

## 二、热门榜单设计：基于 ZSET 的实时排序

热门榜单（如 “本周最受欢迎图书”）需要实时反映用户行为（借阅、查看、评分等），且支持快速排序和 TopN 查询，Redis 的**ZSET（有序集合）** 是最佳选择 ——ZSET 通过 “分数（score）” 排序，可高效实现 “实时加分” 和 “取前 N 名”。

### 1. 核心设计：ZSET 结构与分数规则

#### （1）ZSET Key 与分数定义

- Key：`book:popular:{period}`（按时间维度区分，如`book:popular:week`表示本周热门，`book:popular:day`表示今日热门）；
- 成员（member）：图书 ID（`bookId`）；
- 分数（score）：根据用户行为累加，如：
  - 借阅一次 +5 分；
  - 查看详情一次 +1 分；
  - 评分 4 星以上 +3 分；(分数规则可根据业务权重调整）

#### （2）实时更新分数（用户行为触发）

用户每产生一次 “提升热度” 的行为（如借阅、查看），就调用`ZINCRBY`命令累加分数：

```java
/**
 * 记录用户行为，更新热门榜单分数
 * @param bookId 图书ID
 * @param action 行为类型（BORROW/VIEW/RATE）
 */
public void updatePopularScore(Long bookId, String action) {
    // 根据行为类型确定加分值
    double increment = 0;
    switch (action) {
        case "BORROW": increment = 5; break;
        case "VIEW": increment = 1; break;
        case "RATE": increment = 3; break;
        default: return;
    }
    
    // 更新本周热门榜单（ZINCRBY是原子操作，支持并发）
    String key = "book:popular:week";
    redisTemplate.opsForZSet().incrementScore(key, bookId, increment);
    
    // 可选：设置榜单过期时间（如7天后自动过期，重新计算）
    redisTemplate.expire(key, 7, TimeUnit.DAYS);
}
```

- `ZINCRBY`是原子操作，即使多个用户同时操作同一本书，也能保证分数正确累加（无并发问题）；
- 实时性高，用户行为触发后立即更新，榜单数据延迟极低。

#### （3）查询 TopN 热门图书

前端展示 “Top10 热门图书” 时，通过`ZREVRANGE`（倒序取前 N 名）查询，再结合书目缓存获取详情：

```java
/**
 * 获取本周热门TopN图书
 * @param topN 前N名（如10）
 * @return 图书详情列表
 */
public List<Book> getTopPopularBooks(int topN) {
    String key = "book:popular:week";
    // 步骤1：从ZSET取分数最高的前N个bookId（withScores=false不返回分数）
    Set<Object> bookIdSet = redisTemplate.opsForZSet()
            .reverseRange(key, 0, topN - 1); // 0~9是Top10
    
    if (bookIdSet == null || bookIdSet.isEmpty()) {
        return Collections.emptyList();
    }
    
    // 步骤2：批量查询图书详情（复用之前的缓存方法）
    List<Book> topBooks = new ArrayList<>();
    for (Object bookIdObj : bookIdSet) {
        Long bookId = Long.valueOf(bookIdObj.toString());
        Book book = getBook(bookId); // 从缓存/DB获取详情
        if (book != null) {
            topBooks.add(book);
        }
    }
    return topBooks;
}
```

- 批量查询：若 TopN=10，一次`ZREVRANGE`即可获取 10 个 bookId，避免多次查询；
- 复用书目缓存：`getBook(bookId)`会优先查`book:summary:{id}`，减少 DB 访问。



### 2. 热门榜单的持久化与更新策略

ZSET 数据存在 Redis 内存中，若 Redis 重启会丢失，需结合持久化和定时任务保证数据可用性：

#### （1）持久化方案

- 短期榜单（如今日热门）：依赖 Redis 的 RDB/AOF 持久化，重启后恢复数据；
- 长期榜单（如月度热门）：每天定时将 ZSET 数据同步到 DB（如`book_popular`表），避免丢失：

```java
// 定时任务（每天凌晨2点执行）
@Scheduled(cron = "0 0 2 * * ?")
public void persistPopularBooks() {
    String key = "book:popular:week";
    // 获取所有图书的分数
    Set<ZSetOperations.TypedTuple<Object>> tuples = redisTemplate.opsForZSet().rangeWithScores(key, 0, -1);
    if (tuples != null) {
        // 同步到数据库（伪代码）
        popularMapper.batchInsert(tuples.stream()
                .map(tuple -> new BookPopular(
                        Long.valueOf(tuple.getValue().toString()),
                        tuple.getScore().longValue(),
                        LocalDate.now()
                    )).collect(Collectors.toList()));
    }
}
```

#### （2）榜单滚动更新

避免单一榜单数据累积过大（如 “本周热门” 到周末可能有大量数据），可按时间滚动：

- 每日生成 “昨日热门”，每周生成 “上周热门”，用新 Key 存储（如`book:popular:20240926`）；
- 前端展示时，优先查最新榜单，若为空则查历史数据（如 “本周热门” 为空时，显示上周数据）。

### 可能追问 & 回答要点

- **如何避免缓存穿透？** → 对不存在的 id 可以缓存空对象（短 TTL）或用布隆过滤器防止随机请求打到 DB。
- **如何防止缓存雪崩？** → 设置不同的过期时间（随机化 TTL），在热点 key 上使用持久化或内存优先。
- **热门榜单如何持久化？** → 定时任务把 `ZREVRANGE` 的 TopN 写回 DB 或预先生成页面缓存。

# 3) 鉴权（JWT + 拦截器 + Redis 存 session 的实现细节）

**考点**：认证与授权实现、token 设计、安全、拦截器/过滤器、角色控制。

### 面试答法（背版）

> 我使用 JWT 做无状态认证：登录成功后生成 JWT（包含 userId, role, exp），并把用户信息缓存到 Redis（`login:{userId}`）以便快速拿到用户角色与权限。拦截器在每次请求时先解析 token（验证签名与过期），再从 Redis 校验 token 是否在有效会话列表中（支持登出使 Token 立即失效）。权限控制用注解或在拦截器里判断 role。

### 关键代码（改进版拦截器）

```java
@Component
public class AuthInterceptor implements HandlerInterceptor {
    @Resource
    private RedisTemplate<String, Object> redisTemplate;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        String token = req.getHeader("Authorization");
        if (StringUtils.isBlank(token)) {
            res.setStatus(401); return false;
        }
        try {
            Claims claims = JwtUtil.parseToken(token);
            Long userId = claims.get("id", Long.class);
            // 校验 Redis 中是否有该 session（实现登出）
            Object cached = redisTemplate.opsForValue().get("login:" + userId);
            if (cached == null) { res.setStatus(401); return false; }
            req.setAttribute("userId", userId);
            req.setAttribute("role", claims.get("role"));
            return true;
        } catch (Exception e) {
            res.setStatus(401); return false;
        }
    }
}
```

### 可能追问 & 回答要点

- **JWT 为什么还要配 Redis？不是无状态的吗？** → 用 Redis 支持主动登出、单点登录控制与黑名单（当要立即失效 token 时需要）。
- **如何防止 JWT 被窃取滥用？** → 短期有效（比如 2 小时） + Refresh Token 机制、HTTPS、在 Redis 存白名单并在服务器端校验。
- **如何做基于角色的权限控制？** → 用 Spring Security 或自定义注解 `@RequiresRole("admin")` 在 AOP/拦截器层判断。

# 4) 搜索与分页（MyBatis 动态 SQL，如何支持按书名/作者/分类关键词搜索并分页）

**考点**：MyBatis 动态 SQL、性能（索引/全文检索）、分页插件、复杂查询写法。

### 面试答法（背版）

> 我在 Mapper 中用 MyBatis 的动态 SQL (`<where>`, `<if>`) 实现可选条件组合的查询，同时用 PageHelper 做分页（或 `LIMIT OFFSET`）。对书名/摘要用 MySQL FULLTEXT（`MATCH ... AGAINST`）或日后接 Elasticsearch 以满足更复杂需求。注意对 `ORDER BY updated_at` 建索引以优化分页排序。

### 关键代码（Mapper XML 示例）

```xml
<!-- resources/mapper/BookMapper.xml -->
<select id="searchBooks" resultType="com.library.entity.Book">
  SELECT b.* FROM books b
  LEFT JOIN book_authors ba ON ba.book_id = b.id
  LEFT JOIN authors a ON a.id = ba.author_id
  <where>
    <if test="title != null and title != ''">
      AND b.title LIKE CONCAT('%', #{title}, '%')
    </if>
    <if test="author != null and author != ''">
      AND a.name LIKE CONCAT('%', #{author}, '%')
    </if>
    <if test="category != null and category != ''">
      AND EXISTS (SELECT 1 FROM book_categories bc WHERE bc.book_id = b.id AND bc.category_id = #{category})
    </if>
  </where>
  GROUP BY b.id
  ORDER BY b.updated_at DESC
  LIMIT #{offset}, #{size}
</select>
```

### 服务层分页使用（PageHelper 示例）

```java
PageHelper.startPage(pageNum, pageSize);
List<Book> list = bookMapper.searchBooks(param);
PageInfo<Book> pageInfo = new PageInfo<>(list);
```

### 可能追问 & 回答要点

- **为什么用 FULLTEXT/ES？** → LIKE 在大数据量下慢；FULLTEXT 支持分词与权重；ES 适合高并发、复杂排序与高质量搜索体验。
- **分页深页性能如何优化？** → 用 keyset pagination（基于排序列的 where id < lastId）或预聚合/topN缓存，避免大 offset。

# 5) 单元测试与接口测试（如何保证核心逻辑正确：借还逻辑、并发、缓存失效）

**考点**：测试策略（单元测试 vs 集成测试），Mocking/事务回滚，如何验证并发安全（简单可测方法）。

### 面试答法（背版）

> 我对 Service 层写了单元测试（用 Mockito mock Mapper/DAO），对关键接口写了集成测试（用 SpringBootTest + MockMvc 或使用内存 DB H2），并用事务回滚保证测试隔离。对于并发场景，我用简单的多线程单元测试模拟两个并发借书请求并断言只有一个成功（通过事务+DB 能验证）。

### 关键代码（单元测试与简单并发测试示例）

单元测试（Mockito）：

并发测试（集成测试，H2 或真实 DB）：

```java
@Test
public void testConcurrentBorrow() throws InterruptedException {
    ExecutorService es = Executors.newFixedThreadPool(2);
    CountDownLatch latch = new CountDownLatch(2);
    AtomicInteger success = new AtomicInteger();

    Runnable task = () -> {
        try {
            if (bookService.borrowBook(100L + ThreadLocalRandom.current().nextInt(100), 1L)) {
                success.incrementAndGet();
            }
        } finally {
            latch.countDown();
        }
    };

    es.submit(task);
    es.submit(task);
    latch.await();

    // 期望只有 1 次成功
    Assertions.assertEquals(1, success.get());
}
```

### 可能追问 & 回答要点

- **并发测试如果在内存 DB 上不准确怎么办？** → 内存 DB 行级锁行为可能与 MySQL 不同，最好在测试环境使用真实 MySQL（或 Testcontainers）做集成并发测试。
- **如何做自动化 CI？** → 把测试放到 GitHub Actions / GitLab CI，测试跑完才 merge；可用 Docker Compose 启动依赖服务（MySQL/Redis）。
