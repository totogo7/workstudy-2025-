## 2. 借阅 / 归还 部分如何实现：

“借书我把它当成一个**事务性操作**来做：把书拆成每一一个副本（`book_copies`）进行管理。

借书时会锁定一个可用副本（在数据库里用 `SELECT ... FOR UPDATE`），在同一事务里改状态、写借阅记录并更新书的可借数量，成功后再清理缓存和增加热度；还书就是反向操作，更新副本状态、写归还时间并恢复可借数量，同样做缓存同步。

> 乐观锁适合冲突少的场景，我们借书是强一致性场景，用悲观锁（FOR UPDATE）实现更简单可靠，后期若并发极高再考虑 Redis 预减 + 补偿。

涉及到的数据库有：`books`（书目，总/可借量） + `book_copies`（每册一行，`copy_status` 标示是否可借） + `borrow_records`（借阅日志）

借书流程如下：

1. 前端发请求：`POST /api/borrow?userId=xx&bookId=yy`。
2. 后端开始事务（`@Transactional`）
3. 在 DB 找一条可借的副本并锁行：
4. 如果没找到 → 回滚事务，返回“无可借副本”。
5. 找到后在同一事务里：
   - 把该副本 `copy_status` 标为已借（2）。
   - 插入一条 `borrow_records`（记录借出时间、到期日等）。
   - 把 `books.available_copies = available_copies - 1`。
6. 提交事务；然后在应用层做两件事：**删除/更新缓存（evict）** 和 **`ZINCRBY book:hot` 增加热度**。返回借阅记录 id 给前端。

还书流程：

1. 前端发请求：`POST /api/borrow/return?recordId=zz`
2. 后端开始事务
3. 查找该 `borrow_records`（状态为借出），更新 `return_time` 与 `status` 为已还
4. 把对应的 `book_copies.copy_status` 改回可借（1），并把 `books.available_copies = available_copies + 1`
5. 提交事务，**evict 缓存** 或原子更新缓存的可借数；返回成功

## 3.Redis

Redis 用来缓解数据库读压力、加速热点数据访问（比如图书详情页、热门榜），并能做简单的计数/排名（ZSET）来实现热度排行榜 —— 对比直接读 MySQL，Redis 的响应更快（内存）、并支持原子操作。

> ZSET 原子且支持排名查询

图书缓存服务接口（BookCacheService）

1. 从缓存获取单本图书信息
2. 用缓存旁路模式获取图书（查缓存→未命中查数据库→写入缓存）
3. 清除指定图书的缓存
4. 将图书存入缓存并设置过期时间
5. 获取指定数量的热门图书列表
6. 增加图书的热度评分

实现类`BookCacheServiceImpl`：实现`BookCacheService`接口，基于Redis实现了图书缓存相关操作，核心逻辑包括：

1. **基础缓存操作**：通过Redis存储/获取图书信息（JSON序列化），支持设置过期时间，清除指定图书缓存。 
2. **缓存旁路模式**：查询时先查缓存，未命中则查数据库，再将结果写入缓存；对不存在的图书设置短期空值占位符，防止缓存穿透
3. **热门防缓存雪崩**：设置缓存过期时间时添加随机值（10-15分钟），避免大量缓存同时失效。
4. **热门图书管理**：用Redis有序集合（ZSet）存储图书热度评分，支持增减评分；获取热门图书时按评分倒序取前N名，并批量查询缓存详情。

小结：

1. 缓存策略用 Cache-Aside：读先查 redis → miss 去 DB → 写回 redis；写操作 DB 成功后 evict cache。
2. 缓存对象：图书详情（短中 TTL）、热门榜（ZSET）、可借副本计数可用 Redis 原子操作。
3. 防护：空值缓存、分布式锁（SET NX）、TTL 随机化、防雪崩、降级。
4. 代码要点：`RedisConfig` + `BookCacheService` 抽象缓存细节，`BookService` 只关心业务，减少耦合。
5. 监控/测试要到位——命中率、miss率、redis memory/eviction。

## 6.一些优化策略

- **问题**：最初某些查询使用 `LIKE '%xxx%'` 导致慢查询与全表扫描。
- **我做的优化**：将热点字段做 FULLTEXT（短期）或在关键 WHERE 上建复合索引（如 `book_copies (book_id, copy_status)`），并将搜索需求规划为后期迁 ES。
- **结果**：查询从数秒级降到几十毫秒；并发锁等待显著减少。
