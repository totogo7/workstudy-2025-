## 进程和线程的区别？适用的场景？
- 进程是程序的一次执行，是资源分配的基本单位。线程是比进程更小的执行单位，一个进程在其执行的过程中可以产生多个线程，线程之间共享进程的堆和方法区的资源。我简单理解为，进程相当于一个独立的应用，线程就是应用里的执行线。
- 例如在我之前做的图书管理系统中，整个系统启动是一个线程，但像借书、还书、查询这些操作，我会用多线程来处理接口请求，避免阻塞主线程
- 如果是计算密集型任务，比如大规模数据分析，用多进程可以更好的利用多核cpu，而像io密集型，比如网络请求或数据库交互，就适合用多线程或线程池去优化性能。

## 最有趣的一个bug？
> 有一次在做校园二手交易App的时候，发现收藏的商品数量总是对不上。后来调试发现，是我在多线程访问SQLite数据库的时候，没有加锁控制，导致数据竞争。当时挺有意思的，因为明明逻辑都对，但测试数据一直乱。我最后在写入和读取时加了synchronized锁，并重新测试并发操作，问题就解决了。这件事让我印象挺深的，也让我意识到并发问题在小项目里也会出现。

当时我负责的是商品收藏模块。功能很简单，用户点击收藏按钮就把商品加入收藏列表，再点一次就取消。但我后来测试发现收藏的数量经常对不上，比如点了收藏但界面没变，或者刷新之后数量不对。一开始我以为是UI没更新或者是逻辑判断写错了，就去看了前端交互和数据库日志，我发现问题其实出在多线程并发访问SQLite（我在不同线程里同时堆收藏表进行读写，没有加锁，导致数据竞争。后来我就改成在读写操作上加synchronized控制，确保同一时间只有一个线程能访问数据库。这个bug让我意识到移动端本地数据库也会有并发的风险。查看日志和调试很重要。

> synchronized是java中的一个关键字，主要是解决多个线程之间访问资源的同步性，可以保证被它修饰的方法或者代码块在任意时刻只能有一个线程执行。

```java
public class FavoriteDao {
    private SQLiteDatabase db;

    public FavoriteDao(SQLiteDatabase db) {
        this.db = db;
    }

    // 添加收藏
    public synchronized void addFavorite(String userId, String productId) {
        ContentValues values = new ContentValues();
        values.put("user_id", userId);
        values.put("product_id", productId);
        db.insert("favorites", null, values);
    }

    // 取消收藏
    public synchronized void removeFavorite(String userId, String productId) {
        db.delete("favorites", "user_id=? AND product_id=?", new String[]{userId, productId});
    }

    // 查询用户收藏数
    public synchronized int getFavoriteCount(String userId) {
        Cursor cursor = db.rawQuery("SELECT COUNT(*) FROM favorites WHERE user_id=?", new String[]{userId});
        int count = 0;
        if (cursor.moveToFirst()) {
            count = cursor.getInt(0);
        }
        cursor.close();
        return count;
    }
}
```

## 测试流程的理解
一般的测试流程我理解的是：拿到需求文档，理解功能的逻辑---设计测试用例---测试环境准备---执行测试---提交bug并跟进修复---最后做回归测试

图书项目的测试流程：首先根据需求文档和接口文档，设计测试用例，用等价类、边界值等方法编写测试点（比如图书数量为0，分页的边界，借阅日期格式等），使用postman和jmeter去测试接口的稳定性和性能，发现问题之后会发送信息到群里跟组员讨论，大家表达自己的看法然后我再进行修改，最后进行回归测试。
> 我当时遇到了一个非常奇怪的问题，分页查询的结果不太对，用postman传送pagenum和pagesize去请求数据，结果pagenum=2的时候返回的内容和第一页一样，我一开始以为时前端缓存的问题，后来看日志发现时后端查询语句的分页逻辑写错了——在计算offset的时候写成了pageNum * pageSize，其实应该是 (pageNum - 1) * pageSize

在实习的时候，测试流程就更偏向与实际的生产环境，我们先拿到新机器的测试规范文档，明确测试的项目，比如usb接口，音频，触控板等，准备一些测试工具和软件，进行基础功能测试和稳定性测试，用3dmark等工具，发现问题之后要立刻记录并提交bug，包括问题复现步骤，描述，截图等，提交到系统。开发人员修复之后需要再次验证与回归，确认后会关闭bug。

## 线程池在项目里的应用
我在项目里主要用线程池来处理并发任务。比如在图书系统中，我们有一个定时任务会去检查超期未还的图书并发送提醒，如果直接循环发请求效率太低。
所以后来我用了Executors.newFixedThreadPool()创建固定线程池，把每个用户的提醒任务交给线程池去执行，这样既提高了效率，也能控制线程数量，防止资源被耗尽。
这个应用场景比较典型，也让我更直观地理解了线程池的意义——在性能和资源之间找到平衡。
> 用固定线程池可以让并发量可控，固定线程池能有效限制资源使用，避免线程无限创建导致 CPU 飙高或内存被占满。
> 用户量大我会考虑分批处理，比如分页查询每次处理几百个用户，或者结合
```java
import java.util.*;
import java.util.concurrent.*;

public class OverdueReminderTask {
    // 创建一个固定大小的线程池，最多同时执行 5 个任务
    private static final ExecutorService executor = Executors.newFixedThreadPool(5);

    // 模拟数据库中超期未还的用户列表
    private static List<String> overdueUsers = Arrays.asList("用户A", "用户B", "用户C", "用户D", "用户E", "用户F");

    public static void main(String[] args) {
        // 定时任务：每天检查一次超期图书
        Timer timer = new Timer();
        timer.schedule(new TimerTask() {
            @Override
            public void run() {
                checkAndSendReminders();
            }
        }, 0, 24 * 60 * 60 * 1000); // 每天执行一次
    }

    // 检查并发送提醒
    public static void checkAndSendReminders() {
        System.out.println("开始检查超期用户...");

        for (String user : overdueUsers) {
            executor.submit(() -> sendReminder(user)); // 把每个提醒任务交给线程池
        }

        System.out.println("提醒任务已全部提交。");
    }

    // 模拟发送提醒
    public static void sendReminder(String user) {
        System.out.println("正在发送提醒给：" + user + " | 线程：" + Thread.currentThread().getName());
        try {
            Thread.sleep(1000); // 模拟发送耗时
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        System.out.println("提醒发送完成：" + user);
    }
}

```

> 我在项目里主要用线程池来处理并发任务。比如在图书管理系统中，我们有个定时任务会定期检查超期未还的图书并发送提醒。
一开始我是直接循环去发请求的，但效率太低，后来改成用 Executors.newFixedThreadPool() 创建固定线程池，把每个用户的提醒任务交给线程池去执行，这样既能并发处理，又能控制线程数量，防止资源被耗尽。

除了这个场景，我还在一些异步任务中用过线程池，比如用户借书后要记录日志、更新推荐榜单，这些操作我就放到线程池里后台执行，避免阻塞主流程。

对我来说，线程池的意义就是在性能和资源之间找到一个平衡点，既能提高系统吞吐量，又能保证运行的稳定性。

## 观察者模型适用的地方
观察者模式适合：系统事件驱动的场景——比如“用户下单、书被借出、还书事件发生时，立即通知感兴趣的订阅者（Observer）”。它是推模型，耦合低，实时性好。
